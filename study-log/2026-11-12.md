## 몰랐던 것 → 알게 된 것
- `@TenantId` → Hibernate가 세션을 열 때 리졸버에 현재 현장을 묻고, 그 엔티티의 모든 SELECT에 `site_id = ?`를 붙이고 INSERT 때 값을 채운다. `isRoot`가 true면 조건을 안 붙인다(본사·시스템 작업)
- 현재 현장은 `ThreadLocal`(Node `AsyncLocalStorage`) → Tomcat·컨슈머가 스레드를 재사용하므로 `finally`에서 이전 값으로 되돌린다
- `ZoneCatalog`의 기동 시 `findAll()`도 현장 조건이 붙는다 → 전 현장 구역을 읽으려면 root로 실행해야 한다(4단계)
- 현재 현장은 `@Transactional` 메서드를 부르기 전에 정한다 → 트랜잭션 시작 때 세션이 열리며 Hibernate가 현장을 읽는다
- 시험 스레드의 현재 현장이 1이면 리포지토리로는 현장 B 행이 안 보인다 → 현장을 가로질러 확인할 땐 JDBC로 센다(`@TenantId`가 막는다는 반증)
- 운영 전이면 메시지 형식 전환에 expand/contract가 필요 없다(옛 API가 옛 메시지를 보낼 일이 없음). DB·리졸버 임시 기본값은 운영이 아니라 단계마다 시험이 통과하는 커밋을 위해 둔 것
- 부모의 `protected` 메서드와 같은 시그니처를 자식이 `private`로 다시 만들면 컴파일 에러(접근 범위를 좁혀 덮어쓸 수 없음)
- "쿼리를 직접 쓰지 말라" → 막으려는 건 문자열을 이어 붙인 SQL(인젝션), DB에 묶인 네이티브 SQL, 메서드 이름으로 될 걸 문자열로 쓰는 것. `@Query` JPQL은 파라미터 바인딩이고 기동 때 파싱돼 틀리면 기동 실패. 메서드 이름으로 안 될 때 쓰는 도구(`findAt`의 괄호 묶인 OR가 그 예). 재구성은 장비마다 기존 메서드로 충분
- 트랜잭션 밖에서 LAZY 연관을 읽으면 세션이 닫혀 `LazyInitializationException` → `@EntityGraph`·`join fetch`로 함께 읽는다
- `ApplicationRunner`는 컨슈머가 이미 돌기 시작한 뒤 실행된다 → 재구성과 실시간 갱신이 겹쳐도 Lua의 `recordedAt` 비교가 옛 값을 막는다
- 필터 vs 인터셉터 → 인터셉터는 컨트롤러가 정해진 뒤 돌아 경로 변수가 꺼내져 있고, 던진 예외를 `@RestControllerAdvice`가 받는다. 필터는 URL을 직접 자르고 응답을 손으로 써야 한다(Node `router.param` vs 전역 `app.use`)
- `preHandle`에서 정하고 `afterCompletion`에서 되돌리려면 람다로 못 감싼다 → `AutoCloseable` `Scope`(try-with-resources와 같은 모양)
- `@TenantId`는 DB만 막는다 → 장비 단위 Redis 키(`loc:{id}`)는 꺼낸 값의 `siteId`로 직접 거른다
- 경로 변수에 `{siteId:\d+}` → 숫자가 아니면 매칭 자체가 안 돼 404(없으면 파싱 실패 500)
- Hibernate는 세션을 열 때마다 리졸버에 묻고, Spring Data는 기동 때 `@Query` 검사로 현장 없이 세션을 연다 → 리졸버가 에러를 던지면 기동 실패. 그래서 "아무 현장도 아님"으로 답해 닫힌 쪽으로 실패시킨다(PG RLS에서 설정값이 비면 아무 행도 안 통과하는 것)
- "안 생긴다" 시험은 판정이 고장 나도 통과한다 → 같은 조건에서 "생긴다"는 대조군을 같이 둔다
- `@TenantId` 엔티티는 INSERT 때 현재 현장으로 `site_id`가 채워진다 → 다른 현장 데이터를 시험에서 만들 땐 `SiteContext.run(siteB, …)` 안에서 저장
- 장비가 다르면 파티션이 달라 처리 순서가 보장되지 않는다 → 근접 시험은 앞 장비가 GEO에 들어간 걸 확인하고 다음을 보낸다
- Java `ThreadLocal`은 스레드를 넘지 않는다. Awaitility 조건식은 기본으로 별도 스레드에서 돌아 현재 현장이 없다 → `pollInSameThread()`. 임시 기본값 1이 이걸 가리고 있었다
- `Scope`를 "지우기"가 아니라 "이전 값으로 되돌리기"로 만들어 둬서, 시험의 현장 1 안에서 root로 들어갔다 나와도 현장 1이 유지된다
- 다른 스레드에서 난 예외는 `Future.get()`이 `ExecutionException`으로 감싼다 → `hasCauseInstanceOf`
- 기능별 패키지(package-by-feature)는 맞는 방향. 하위 패키지(`location.ingest`)는 Java에선 별개 패키지라 package-private을 `public`으로 열어야 한다 → Spring Modulith가 경계를 시험으로 지킨다
- Gradle은 입력이 안 바뀌면 시험을 다시 돌리지 않는다(up-to-date, 1초) → 로그를 다시 보려면 `cleanTest test`

## 틀렸던 것 → 바로잡힌 것
- 면접 1 "시험 트랜잭션 롤백이 안 되는 이유"를 "MySQL이 롤백이 안 돼서" → MySQL은 데이터 변경(INSERT·UPDATE·DELETE)은 롤백된다. 안 되는 건 구조 변경(DDL). 시험 롤백이 안 통하는 건 저장이 컨슈머 스레드의 다른 트랜잭션에서 커밋되기 때문(시험이 넣은 장비는 커밋 전이라 컨슈머에게 안 보임, Redis는 롤백 없음)
- 면접 2 "출발할 때 timestamp를 찍는다"는 맞음(`recordedAt`이 기준). "GET→비교→SET은 도착 순서만 가능"은 틀림 → 그것도 `recordedAt`으로 비교한다. 문제는 GET과 SET 사이의 틈에 다른 스레드(조회 API의 캐시 미스 채우기)가 끼어드는 것 → Lua로 비교와 쓰기를 한 번에
- 2단계에서 `cleanUp()`에 `DELETE FROM site WHERE id <> 1`이 빠짐 → 현장을 만드는 시험이 둘이 되자 `test-site-b` 이름 중복으로 실패(시험 순서에 따라 드러나는 격리 실패). `site`는 기본 현장 1 때문에 TRUNCATE 대신 DELETE
- 면접 3 "제2서버에 마이그레이션 후 스위치"는 앱 서버 배포 방식 → 보통 DB는 서버들이 같이 쓴다. 롤링 배포 중엔 옛 코드와 새 코드가 같은 표를 동시에 쓰므로 expand(기본값과 함께 INSTANT 추가) → 코드 전환(서버 하나씩) → contract(기본값 제거)
