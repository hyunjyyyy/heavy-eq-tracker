## 몰랐던 것 → 알게 된 것
- 커넥션 풀, HikariCP, 싱글턴이 뭔지 → 내 Node 서버의 `pg.Pool({max:5})`가 풀, `db.js` 모듈 캐시가 싱글턴이었다
- Tomcat → Boot 내장 HTTP 서버. 요청마다 스레드 배정(기본 200). Node 단일 스레드와 달리 `@Service` 빈 안의 Map은 동시 수정된다
- N+1 → 이벤트 100건 조회 + 장비 100번 조회. JPA가 내가 안 썼는데 만든다
- DTO → API 경계의 JSON 모양. 단말 필드명이 바뀌어도 DB는 안 건드린다
- `data class` → equals/hashCode를 모든 필드로 만든다. 엔티티는 id가 정체라 안 맞고, DTO엔 맞다
- 201 vs 202 → 지금 만들었다 vs 받았고 나중에 처리한다. 오늘은 201, Kafka 뒤엔 202
- `application.yml`이 어디 있는 뭔 파일인지 → `src/main/resources/`, `.env`+초기화 코드의 역할
- Flyway 이력 표 → `flyway_schema_history`. 내가 직접 만든 도구의 "적용된 파일 목록"이 이것
- Spring은 `.env`를 읽지 않는다 → compose만 읽는다. 시험은 compose를 안 띄운다
- `bootRun` 85%에서 멈춘 것 → 서버가 떠 있는 상태

## 틀렸던 것 → 바로잡힌 것
- 없는 빈을 생성자로 요구하면 "요청 때 실패" → 기동 때 실패 (`NoSuchBeanDefinitionException`)
- `ddl-auto: validate`에서 표에 열이 있고 코드에 없으면 실패 / 반대면 성공 → 거꾸로. validate는 "코드 → 표" 방향만 본다
- "MySQL은 롤백이 안 돼서 파일을 쪼갰다" → 롤백은 된다. DDL만 트랜잭션에 안 들어간다
- 단말 필드명이 바뀌면 DTO가 있어도 "DB 컬럼명만 바꾸면" → DB는 안 건드린다. DTO 한 곳만
- 모든 요청에 요청 ID 붙이기를 Interceptor에 → Filter. Interceptor는 핸들러가 정해진 뒤에만 돈다
- Redis 자동 구성 조건 클래스를 `HikariDataSource` → `RedisOperations`. 조건 종류(`@ConditionalOnClass`)는 맞았음
- 내가 `DataSource` 빈을 만들면 Boot 것이 "덮어씌워진다" → Boot 것이 아예 안 만들어진다(`@ConditionalOnMissingBean`). 덮어쓰기는 Boot가 기본적으로 금지
- Service의 `ingest`에서 조회 결과를 변수에 안 담고 `if (x() != null)`만 → 담아야 id를 꺼낸다. `try {} throw`는 Kotlin 문법 아님
