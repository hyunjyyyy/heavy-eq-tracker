## 몰랐던 것 → 알게 된 것
- `record` → 선언이 곧 생성자·접근자·equals/hashCode. 접근자는 `eventId()`, `get` 접두사 없음
- `Optional.orElseThrow(() -> new X())` → Kotlin `orElseThrow { X() }`의 Java 람다
- DB NOT NULL 열은 `double`/`boolean`(primitive), NULL 허용은 `Double`, DB가 채우는 id는 `Long` → 타입이 제약을 대신한다
- Java 생성자엔 named argument·기본값이 없다 → 인자 9개 순서를 Service와 맞춰야 하고 `lat`/`lon`이 바뀌어도 컴파일러가 못 잡는다
- Java는 public 클래스 하나 = 파일 하나 → `IngestResult`, `EquipmentNotFoundException`을 별도 파일로
- Redis가 뭔지 → 내 Node 메모리 Map을 프로세스 밖으로 꺼낸 것. 서버 두 대가 같은 Map을 본다
- "명령 하나는 원자적"인데 왜 GET→SET 사이에 끼어드나 → 원자적인 건 명령 **하나**. 두 명령 사이는 아니다. 그래서 `SET NX`
- TTL이 지나면 "Redis 겹이 사라진다"의 뜻 → 안전성이 아니라 빠른 길이 사라지는 것. DB 조회(②)와 UNIQUE(③)가 받는다
- Redis 호출을 `@Transactional` 밖으로 빼려면 왜 클래스를 나누나 → 같은 클래스 안 호출은 프록시를 안 거쳐 `@Transactional`이 무시됨(self-invocation)
- 캐시에 넣는 것도 DTO → 엔티티를 직렬화하면 LAZY 필드가 getter에 걸리고, DB 스키마 변경이 캐시 JSON을 깨뜨림
- 운영 문제는 언제 고려하나 → 기획서가 아니라 구성 요소마다 같은 질문 6개(죽으면/느리면/두 번이면/순서 바뀌면/재시작되면/두 대면)를 설계 때 적어 두는 것
- Boot 4에서 Redis 자동 구성 이름은 `DataRedisAutoConfiguration`, 리포트엔 `#stringRedisTemplate`(소문자)

## 틀렸던 것 → 바로잡힌 것
- "Boot가 DataSource를 알아서 만든다"의 조건을 못 댐 → `@ConditionalOnClass(HikariDataSource)`, `@ConditionalOnMissingBean(DataSource)`, `@ConditionalOnProperty(spring.datasource.type)`. 조건 통과와 실행 성공은 다른 단계
- 운영 DB의 적용된 V1 오타를 "직접 고치고 docker down" → 운영에선 V2뿐. docker down은 로컬 컨테이너 얘기
- 엔티티에 data class를 안 쓰는 이유를 "앱끼리 공유하는…" → 그건 DTO의 T. 이유는 (1) id가 null→42로 바뀌어 hashCode가 깨짐 (2) equals/toString이 LAZY 필드를 읽어 쿼리가 나감
- `Zone.kind`를 `String` + `@Enumerated` → `@Enumerated`는 enum 필드에만. `ZoneKind`
- `Boolean active` → NOT NULL 열이라 `boolean`
- `LocationEvent`에 `@Table(name = "zone")` 복사 흔적, `Long equipmentId`, 열 셋 누락(`h_accuracy_m`, `recorded_at`, `idempotency_key`) → `location_event`, `@ManyToOne(LAZY) Equipment`, 열 추가
- `SET NX`에서 nil을 받은 B 서버는 "60초 뒤 다시" → B는 기다리지 않는다. `GET`해서 eventId면 200, processing이면 409를 지금 돌려준다. 재시도는 단말이
- `DEL`을 빼먹으면 무슨 일이 생기나 → 몰랐음. 키가 processing으로 TTL 내내 남아 재전송 전부 409. 저장 실패 시 선점 해제는 내가 써야 한다
- `IdempotencyStore`를 Service가 어떻게 받나 "bean 관련" → `@Component`로 빈 등록, 생성자 파라미터 타입으로 주입. 템플릿 → Store → Service 순서
- 캐시 전용 record를 쓰는 이유 "캐시니까" → LAZY 필드·스키마 결합 (위)
- Redis에 키가 안 생김(`KEYS` empty, `CLIENT LIST`에 앱 없음) → Rename 때 IntelliJ가 Controller 참조를 `LocationEventWriter`로 바꿔 Redis 단계를 건너뜀. `git status`에 Controller가 M으로 떠서 발견. 디버깅 순서: 증상 → 연결 여부(CLIENT LIST/MONITOR) → 코드가 실행되는지(git status·컴파일 산출물)
