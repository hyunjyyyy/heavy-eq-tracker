## 몰랐던 것 → 알게 된 것
- Spring Modulith 모듈 = 앱 패키지 바로 아래 패키지. 맨 위 패키지는 공개, 하위 패키지는 내부. Java `public`이어도 다른 모듈이 내부를 쓰면 `verify()` 실패(컴파일은 됨). 하위 패키지 일부를 공개하려면 `@NamedInterface`(Node `package.json`의 `exports`)
- `public static final String` 상수는 컴파일 때 쓰는 쪽에 값이 복사된다(상수 인라인) → 바이트코드에 원래 클래스 참조가 없어 Modulith·ArchUnit이 그 의존을 못 본다. `location → common.KafkaTopicConfig`가 안 보여 순환이 아니었다
- 한 방향 의존은 Modulith 기본 규칙에서 위반이 아니다. "common은 아무것도 의존하지 않는다"는 우리가 정하는 규칙이라 `@ApplicationModule(allowedDependencies = {})`로 적어야 시험이 잡는다. 기본값은 제한 없음(`OPEN_TOKEN`), 빈 배열은 의존 금지
- `package-info.java`는 패키지 자체에 어노테이션을 붙이는 파일
- `git mv`로 옮기면 이름 바꿈(R)으로 기록돼 파일 이력이 이어진다
- 하위 패키지로 나눌 땐 하위끼리도 서로 가리키지 않게 한다 → 양쪽이 쓰는 타입은 받는 쪽에 두고(`LocationRecorded`), 다른 하위의 형식을 아는 변환은 그 형식을 가진 쪽으로 옮긴다(`LocationMessage.of`)
- 시험을 같은 하위 패키지로 옮기면 package-private을 열지 않아도 된다(`ConsumerErrorConfig.retryBackOff()`)
- `@NamedInterface`를 클래스에 붙이면 같은 이름끼리 한 공개 창구가 되고, 같은 패키지의 나머지는 내부로 남는다
- 바이트코드만 보는 도구는 컴파일러가 지운 의존을 못 본다 → 순환 재확인은 소스 기준으로도
- 스쿼시 머지된 브랜치는 커밋 해시가 달라 `main..브랜치`에 커밋이 남아 보인다 → 지우기 전 "브랜치 끝 = PR head"와 "스쿼시 커밋이 main에 있음"으로 확인
- 시험 없는 엔드포인트를 옮길 땐 먼저 지금 동작을 시험으로 고정하고 옮긴다
- 모듈끼리 서로 부를 일이 생기면 직접 호출은 순환을 만든다 → 동기 이벤트로 바꾸면 의존이 한 방향이고 트랜잭션도 같다(#24 `LocationSaved`와 같은 모양)
- 확인과 변경 사이 틈(동시 이동) → 비관적 락(`SELECT … FOR UPDATE`)으로 순서를 세우고, DB 제약으로 안전망. MySQL엔 PG `EXCLUDE`·부분 유일 인덱스가 없어 생성 열(`VIRTUAL`) + 유일 인덱스로 흉내(유일 인덱스는 NULL끼리 겹침 허용)
- Hibernate는 모아 둔 변경을 INSERT → UPDATE 순으로 보낸다 → "닫고 새로 열기"는 닫은 뒤 `flush()`해야 유일 제약에 안 걸린다. `save`는 INSERT가 미뤄질 수 있어 예외 시험엔 `saveAndFlush`
- Spring Data 메서드 이름에서 `find`와 `By` 사이 말은 무시된다 → `findWithLockById` + `@Lock`이면 `@Query` 없이 `SELECT … FOR UPDATE`
- 확인과 판정 사이에 다른 트랜잭션이 끼어들 수 있으면 같은 잠금을 양쪽에서 잡는다 → 둘 중 하나가 먼저 끝나고, 나중 것은 바뀐 상태를 본다(이동이 먼저면 기록만, 저장이 먼저면 이동이 그 결과까지 정리)
- 설정 계층: 현장 값 ?? yml 기본값을 항목마다. 다른 값에서 계산되는 반경은 합친 결과에서 계산
- 캐시 무효화는 커밋 뒤에 → 트랜잭션 안에서 지우면 커밋 전에 다른 스레드가 옛 값을 다시 캐시에 넣는다. 이벤트 + `AFTER_COMMIT`(Redis 갱신과 같은 원칙). 무효화 시험은 캐시를 먼저 채운 뒤 바꿔야 의미가 있다
- `@Positive`는 null을 통과시킨다 → "비우면 기본값, 넣으면 양수"가 한 줄
- 메모리 캐시는 시험이 DB를 비워도 앱과 함께 살아남는다 → 시험 기반 `cleanUp()`에서 같이 비운다(`ZoneCatalog.reload()`와 같은 이유)
- 동시성 시험: `CountDownLatch`로 여러 스레드를 한 번에 출발시킨다(Node `Promise.all`). 새 스레드엔 현재 현장이 없어 `SiteContext.call`로 직접 정한다

## 틀렸던 것 → 바로잡힌 것
- (Claude) 동시 이동 시험에 `invokeAll(…, 0, null)`을 써서 바로 터짐 → `invokeAll`은 끝날 때까지 기다린다. 넣기만 하고 바로 돌아오는 `submit` 두 번 → `countDown()`으로 동시에 출발
- 근접 리스너를 넣었는데 파일이 디스크에 저장되지 않아 시험이 옛 코드로 돎 → 수정 시각·`git status`로 확인
- 새 writer 코드를 `LocationEventConsumer.java`에 붙여 넣어 컨슈머 클래스가 사라짐 → "public 클래스는 같은 이름 파일에" 컴파일 에러. 컨슈머는 마지막 커밋으로 되돌리고 writer 파일에 넣음
- (Claude) 경계 시험이 지금 순환을 잡아 실패할 거라 했는데 통과 → 상수 인라인으로 의존이 사라져 있었다. 실패를 기대한 시험이 통과하면 시험이 무엇을 보는지부터 확인한다
- 확인 1 "수집 API가 Kafka에만 넣는 이유"를 "중복 쓰기 방지" → 중복(같은 걸 두 번)이 아니라 이중 쓰기(DB와 Kafka 두 곳에). 한쪽만 성공하면 둘이 어긋난다. 같은 걸 두 번 막는 건 멱등키
- 확인 2 "판정은 같은 트랜잭션, Redis는 커밋 뒤" → 판정 기록(ENTER/EXIT/NEAR)은 위치 행과 함께 커밋·롤백돼야 "판정 없는 위치"·"없는 위치의 판정"이 안 생긴다. Redis는 롤백이 없어 커밋 전에 바꾸면 롤백된 위치가 캐시에 남는다
- 확인 4 기억 못 함 → Hibernate는 세션을 열 때(= `@Transactional` 시작) 현재 현장을 한 번 읽고 세션 중엔 못 바꾼다. `save()` 안에서 정하면 세션은 이미 -1로 열려 저장이 FK로 실패한다
- 확인 5 기억 못 함 → `@TenantId`는 Hibernate 쿼리만 막는다. Redis·JDBC는 못 막는다 → GEO는 `fleet:{siteId}`로 키를 나누고, 장비 단위 `loc:{id}`는 꺼낸 값의 `siteId`로 거른다
