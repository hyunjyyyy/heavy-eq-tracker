## 몰랐던 것 → 알게 된 것
- "경계는 밖"이 아니라 반열림 → `(yi > py) != (yj > py)` 때문에 위·오른쪽 경계는 밖, 아래·왼쪽은 안. 맞닿은 두 구역의 경계선 위 점이 정확히 한쪽에만 속한다
- 진입/이탈은 "지금 안"이 아니라 "이전과 다름" → 이전 상태를 어딘가 들고 있어야 하고, 메모리면 Node에서 서버를 못 늘린 그 구조. 같은 장비 = 같은 파티션 = 같은 컨슈머라 두 대 경쟁은 없지만 재시작·리밸런스에서 사라진다 → DB 원본
- 구역 목록(설정)은 메모리에 둬도 되고 장비 상태는 안 되는 이유 → 어긋났을 때 전자는 "잠깐 옛 설정", 후자는 사건 중복·누락
- 좌표 순서 뒤집힘(GeoJSON `[lon,lat]`)은 에러 없이 전부 "밖" → 범위 검사(위도에 127이면 실패)를 로딩 한 곳에
- 시험 파일은 `src/test/java`에만 JUnit이 보인다 → `src/main`에 두면 `package org.junit.jupiter.api does not exist`. IntelliJ가 Hibernate Validator 내부 `assertTrue`를 제안한 것도 같은 이유
- `Multiple Spring Data modules found, entering strict repository configuration mode` → JPA·Redis 둘 다 있어서 Repository 소속을 엄격히 가린다는 정상 로그
- Remote Control 폴더가 `cannot_be_used: not_available` → 클라우드 세션에서 회사 PC 폴더를 못 연다. 코드 리뷰는 푸시 후
- 평면 거리가 서울에서 동서 방향 26 % 과대 → 경도 1도 길이가 cos(위도)배. 0.0001° = 11.1 m가 아니라 8.8 m
- 임계값에 두 장비 오차를 더하는 이유 → 더하면 헛경보, 안 더하면 놓친 충돌. 전자가 안전한 실수
- 쌍을 정규화하지 않으면 → (7,8) NEAR 뒤 (8,7)에서 상태를 못 찾아 NEAR 중복, CLEAR 중복. (min,max) 규칙
- Redis GEO는 52비트 geohash로 양자화 → 좌표가 0.3 m쯤 틀어지고 거리 오차 0.5 m. RTK 2 cm 정밀도는 GEO에서 사라진다. 예상 5.3 m가 5.52 m로 나온 이유
- 자기 위치는 판정 시점에 아직 GEO에 없다 → `FROMMEMBER`가 아니라 `FROMLONLAT`, 결과에서 자기 자신 제외
- Spring Data의 `Metrics`에는 `METERS`가 없다 → Redis 단위는 `RedisGeoCommands.DistanceUnit.METERS`
- MySQL FK 제약 이름은 DB 전체에서 유일 → V6·V7에 `fk_geofence_event_*`를 복사해 썼으면 적용 실패. `fk_<표>_<참조>` 규칙
- Java `final` 필드를 생성자에서 대입 안 하면 컴파일 에러 → `this.proximityService = ...` 누락이 "related problem"으로 잡힘. Kotlin 주 생성자였으면 생길 수 없는 실수
