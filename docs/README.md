# Dev Notes — heavy-eq-tracker

건설 중장비 위치 관제 서비스를 Kotlin · Spring Boot로 만들면서
**무엇을 만들었는가**보다 **어떤 문제를 어떻게 인식했고, 왜 그렇게 판단했는가**를 남기는 기록이다.

Node.js + Express + PostgreSQL로 실무 서버를 혼자 만들어 운영한 경험이 있고, Spring은 이 프로젝트가 처음이다.
그래서 모든 기록은 "Node에서는 이랬는데 Spring에서는 이렇다"는 대비를 기준으로 쓴다.

<br>

## 📂 기록 구성

### 01_context.md
- 왜 이 프로젝트를 하는가, 목표 공고와 기간
- 가진 것(Node 운영 경험)과 없는 것(Spring, MySQL 튜닝, Kafka)
- 스택과 버전을 고른 기준

### 02_problem-observation.md

- 에러 로그를 어떻게 읽었고 원인이 무엇이었는지
- Node 습관이 Spring에서 깨진 순간

### 03_decision-log.md
- 번호 매긴 설계 결정과 판단 이유
- GitHub 이슈 댓글(결정 하나 = 댓글 하나)을 옮겨 적은 것

### 04_tradeoffs.md
- 각 결정으로 얻은 것 / 포기한 것
- 나중에 결정이 뒤집힐 조건

### 05_learnings.md
- 기술보다 기준이 어떻게 바뀌었는가

## ✍️ 기록 원칙

- 결과가 없어도 기록한다. 실패한 마이그레이션, 잘못 들어간 커밋도 02에 남긴다
- 결정에는 반드시 대안과 "왜 그 대안을 안 골랐는지"를 붙인다
- 측정 수치는 전후를 같이 적는다 (쿼리 수, EXPLAIN rows, 응답 시간)
- 회사 코드·데이터는 들어오지 않는다. Node 서버 얘기는 구조만 추상화해서 쓴다
